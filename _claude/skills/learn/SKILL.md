# learn

このセッションの会話全体を振り返り、次のセッション以降に役立つ学びだけを LEARNING.md に残す。
LEARNING.md はセッション開始時に SessionStart hook が全文をコンテキストへ注入するので、
**短く、重複なく、事実だけ** を書く。

## 手順

### 1. 対象ファイルを決める

次の順で決め、以降 `$LEARNING` として扱う。

1. 引数 `$ARGUMENTS` があればそのパス
2. SessionStart で注入された `[LEARNING.md 読み込み済み] <path>` の path
3. どちらも無ければ `~/.claude/scripts/learning.sh path` の出力（main worktree のルート）

### 2. 既存の内容を読む

- `$LEARNING` を読む。無ければ末尾のテンプレートで新規作成する
- プロジェクトの CLAUDE.md（ルートと `.claude/CLAUDE.md`）も読む。そこに既に書いてあることは学びにしない

### 3. 学びの候補を洗い出す

セッションの最初から最後までを振り返り、4 つのセクションに分けて候補を挙げる。

| セクション | 入るもの |
|---|---|
| 失敗と対策 | うまくいかなかった手順・誤った前提と、次回どうすれば避けられるか |
| 業務知識 | ドメイン用語、業務ルール、外部システムの仕様など、コードからは読み取れない知識 |
| プロジェクト固有の作法 | ブランチ運用、レビュー慣習、テストの回し方、命名や配置の暗黙ルール |
| その他 | 上記に入らないが、次回も役立つと確信できるもの |

採用する基準（すべて満たすもの）:

- 次のセッションで同じ失敗・同じ調査を避けられる
- コード、git 履歴、CLAUDE.md、rules を読んでも分からない
- このプロジェクトで再び役立つ（今回のタスク限定の事実ではない）

除外するもの:

- 今回のタスク固有の進捗や結論
- 一般的なプログラミング知識・言語仕様
- コードを読めば分かるディレクトリ構成や関数の説明
- 秘匿情報（トークン、パスワード、個人情報）
- 確認していない推測

### 4. 既存項目と照合する

- 文言ではなく「原因」と「対策」で比較する。対象のコマンドやファイルが違っても、原因と対策が同じなら同じ項目とみなす
- 同じ項目なら追記しない。新しい事例で既存項目の適用範囲が広がるなら、既存項目を下の「抽象度の決め方」に沿って書き換える
- 既存項目をより正確にできるなら、その項目を書き換える
- 既存項目と矛盾するなら、現状を確認したうえで新しい内容に書き換える

### 5. 書き込む

- 1 項目 1 行（長くても 2 行）。`- <事実> → <どうするか>` の形
- 抽象度は下の「抽象度の決め方」に従う
- セクション見出しは固定。空のセクションも残す
- `<!-- last-reviewed: ... -->` の行は触らない（週次レビューが更新する）
- 日本語と半角英数字の間に半角スペース

### 6. 全体を読み直して抽象化する

今回の学びの有無にかかわらず、書き込み後の `$LEARNING` を全項目読み直す。

- 具体例のままの項目は、他と重ならない 1 件でも「抽象度の決め方」に沿って書き換える
- 原因と対策が同じ項目が複数あれば 1 項目にまとめる
- 事実は変えない。判断に迷う項目は書き換えずに残す
- 削除はしない。古い項目や CLAUDE.md に取り込み済みの項目の削除は `/learn-review` が行う

### 7. 報告する

- 追加・更新・抽象化のどれも無ければファイルに触らず「LEARNING.md: 追加なし」と 1 行で報告する
- あれば「LEARNING.md: 追加 n 件、更新 m 件、抽象化 k 件」に続けて、追加・更新・抽象化した項目を 1 行ずつ列挙する
- headless（hook からの自動実行）でも同じ形式で報告する。報告は log に残る

## 抽象度の決め方

具体例そのままの項目は、同じ原因で起きる別の事象に当てはめられず、事例ごとに項目が増えてしまう。そのため原則は抽象化し、値そのものが知識であるものだけを具体のまま残す。

この判断は Opus / Fable 相当のモデルが行う前提で書いている。下の項目は判断の観点であって網羅的な規則ではない。列挙に当てはまらない項目は「次のセッションで読んだときに、類似の事象にも正しく適用でき、かつ具体値が必要な場面で困らないか」という目的に照らして判断する。他のモデルで実行される場合もこの基準を下げたり、機械的な規則に置き換えたりしない。

- 「原因 → 対策」は、同じ原因で起きる類似の事象にも当てはまる粒度で書く。具体例は末尾の括弧に最小限だけ添える
  - 例: `- 権限が要る操作や Bash tool で拒否される操作は自分で実行できない → スクリプトを用意してユーザーに別ターミナルで実行してもらう (例: sudo、~/.claude 配下の rm)`
- 次のものは抽象化せず具体のまま書く。抽象化すると使えなくなるため
  - バージョン、パス、コマンドのフラグ、パッケージ名など、その値自体が知識であるもの
  - ユーザーが下した個別の判断（残すと決めたパッケージなど）
  - 外部システム固有の仕様や挙動
- 抽象化した結果、別の項目と原因・対策が重なるなら 1 項目にまとめる。その項目が持っていた具体値は括弧の例に移す
